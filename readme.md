# Тестовые артефакты на примере сервиса Яндекс погода

Проект создан как портфолио для демонстрации навыков работы с требованиями и артефактами тестирования.

## Цель проекта
Проект создан для демонстрации навыков работы с требованиями и тест-дизайном. В нём показана цепочка: от User Story до выделения атомарных требований и покрытие требований тест-кейсами. Для прослеживаемости все артефакты пронумерованы и дополнительно добавлена матрица трассируемости. 

## Как происходила работа над проектом
1. Были сформулированы интуитивные требования к функционалу от лица пользователя.
2. Далее интуитивные пользовательские ожидания были трансформированы в формализованные требованияч, опираясь на техническую документацию экосистемы Яндекса.
3. На основе документации составлены критерии приёмки для выделенных требований.
4. На основании выделенных критериев приёмки и требований были составлены тест кейсы.

В процессе работы использую документацию вендора как источник истины для валидации тестовых артефактов.

## Структура проекта
Артефакты в проекте разложены по директориям. Вот как можно найти нужный тип документа:
- `requirements/` — Требования (файлы `REQ-*.md`) с критериями приёмки. Требования оформлены по единому шаблону.
- `test-cases/` — тест-кейсы (файлы `TC-*.md`), оформлены по единому шаблону.
- `docs/` — шаблоны документации (для требований, тест кейсов и user story). Для создания новых артефактов используются эти шаблоны.
- `coverage/` — матрицы трассируемости (в формате Markdown), показывающие связь требований с тест кейсами и связь user stories и требований.
- `user_stories/` — исходные User Story, из которых были выведены требования. файлы `US-*.md` оформлены по единому шаблону.

## Как отследить связь: User Story → REQ → TC
Связи между требованиями показаны как связь требования с конкретным модулем и указание зависимостей между модулями и самими требованиями.
Информация представлена в файле `coverage/matrix_REQ_to_REQ.md`
Здесь Module - название модуля к которому относится требование
- *Req ID* - идентификатор требования
- *Summary* - краткая информация о требовании
- *Dependencies* - модули от которых зависит требование
- *Impact on Other Modules* - модули на которые повлияет изменение этого требования

| Module | Req ID | Summary | Dependencies | Impact on Other Modules |
| --- | --- | --- | --- | --- |
| main | REQ-main-001 | Погода на главной странице | - | search, map, menu |
| main | REQ-main-002 | Дополнительные инструменты на главной странице | - | search, map, menu |

Здесь показан фрагмент связи на примере одной пользовательской истории.
Для отслеживания связи с требованиями нужно посмотреть информацию в матрице трассируемости - файл `coverage/matrix_US_to_REQ.md`
- *user story ID* - идентификатор пользовательской истории
- *Описание user story* - краткое описание пользовательской истории
- *Requiement ID* - идентификатор связанного требования
- *Комментарий* - комментарий про причину связи

| user story ID | Описание user story | Requiement ID | Комментарий |
| --- | --- | --- | --- |
| US-weather-001 | Прогноз погоды около дома | REQ-main-001 | Прогноз погод отображается на главной странице |
| US-weather-001 | Прогноз погоды около дома | REQ-main-002 | Чтобы уточнить точнее указать место пользователь может воспользоваться поиском|
| US-weather-001 | Прогноз погоды около дома | REQ-search-003 | Пользователь явно может указать свой населённый пункт |
| US-weather-001 | Прогноз погоды около дома | REQ-search-004 | Пользователь может выбрать населённый пункт из списка |

Для отслеживания покрытия требований тест кейсами - нужно найти требование в таблице и посмотреть на наименование файла тест кейса.
Смотри файл `coverage/matrix_REQ_to_TC.md`
- *Requiement ID* - идентификатор требования
- *Описание Requiement* - его краткое описание
- *test case ID* - идентификатор тест кейса
- *Тип теста* - Позитивный или негативный тест
- *Приоритет теста* - приоритет тест кейса
- *Проверяемая версия* - какую версию проверяет тест - полную, мобильную (адаптированную под экран смартфона), или обе
- *Дата актуализации* - дата последней актуализации тест кейса

| Requiement ID | Описание Requiement | test case ID | Тип теста | Приоритет теста | Проверяемая версия | Дата актуализации |
| --- | --- | --- | --- | --- | --- | --- |

## Как пользоваться шаблонами
Короткая инструкция для использования шаблонов:
1. Скопировать файл шаблона из директории `docs/`.
2. Переименовать его - по формату указанному в файле шаблона - например из `template_test_cases.md` в `TC-XXX.md` Где XXX - текущий номер тест кейса. 
3. Заполнить поля строго по структуре следуя подсказкам в документе.
4. Для тест кейса или требования обязательно указывается ID связанного с документом требования или пользовательской истории.
5. Заполнить информацию в матрице трассируемости - это позволит в дальнейшем отследить конкретный артефакт.

## Workflow в Git
Для данного проекта используется следующий подход: для каждого процесса создаётся отдельная ветка. После проверки и согласования делается Pull Request в ветку `main`. Ветки после merge удаляются. История коммитов линейная.

## Как проводилось тестирование
Для данного проекта тест кейсы расчитаны на прохождение тестов в 4 разных браузерах, на двух платформах (mobile и desktop) а также разбиты на 4 модуля. Поэтому тестирование я проводил с использованием попарного тестирования. Благодаря попарному тестированию число тестовых прогонов удалось сократить с 32 до 16.
- Список платформ и тестов расположен в `docs/Pairwise_test.md`
- Отчеты по тестированию располагаются в директории `/reports` . Каждой из строк таблицы `Pairwise_test.md` соответствует отдельный файл отчета.
- Тесты которые не были пройдены успешно- были пройдены повторно на каждой из платформ для локализации дефекта и составления баг репорта.
- Баг репорты лежат в директории `/bug_reports`
